# ZMeta v1.1.19 Release Notes

Release date: 2026-07-27
Release type: consumer-access and verification-integrity cut — the governed
policy as JSON, and the guards that keep current-facing claims honest

## Summary

v1.1.19 is a small release with one new artifact and a set of guards, and
both came from outside. A fielded deployment advancing its ZMeta pin reported
a defect in our published records, and the same review surfaced the reason
that deployment had been hand-copying governed data for months.

The artifact is `export/policy/*.json`: the governed policy, verbatim, in a
format a consumer outside the Python stack can read. The guards are the
answer to a harder question — why several current-facing claims in this
repository were wrong while every check was green.

No schema, policy data, or event-vocabulary changes; `policy/README.md`
gained a pointer to the JSON projection. The locked v1.0 kernel is unchanged.

## The governed policy, readable without a YAML parser

`export/policy/*.json` is a generated, verbatim JSON projection of
`policy/*.yaml` — one file per source file, same name, same data, nothing
renamed, filtered, flattened, or interpreted. `yaml.safe_load` of a source
and `json.load` of its export compare equal, and a test pins that per file.

- Generated by `tools/export_policy_json.py`; verify with `--check`.
- Hash-pinned in the release manifest under the new `policy_json_export`
  artifact group, and carried in the release bundles.
- Provenance in `export/policy/index.json`: source path and LF-normalized
  SHA-256 per file.
- **Authority is one-directional.** `policy/*.yaml` is the source of truth.
  Editing a JSON file here does not change policy; it produces a stale file
  that `--check` fails on.

**Why it exists.** Until now a consumer outside Python had two options:
vendor a YAML parser alongside the raw files, or hand-copy the parts it
needed. Hand-copying is what happened — a fielded deployment was mirroring
the semantics-contract §7.7 STATE denylist in TypeScript and re-verifying
that alignment by hand at every version advance. That is not a discipline
failure on their side; copying was the only path this repository offered.
A hand-copy of governed data is a private dialect forming around the honesty
primitives, and the burden grows with every consumer.

**If you maintain such a copy, consume this instead** and regenerate on each
version advance rather than re-verifying an alignment by hand.

It is deliberately not a curated bundle. Folding the schema's controlled
vocabularies in alongside would mean judging what a consumer needs, which
creates a third artifact that can drift from both parents.

## Record correction: the published v1.1.17 and v1.1.18 READMEs

Both published trees carry a stale README "Release focus" bullet describing
v1.1.16's external capture corpus and asserting *"No schema, policy, or
event-vocabulary changes."* That was true of v1.1.16 and **false of both
releases that inherited it**: v1.1.17 added three `reason_code` values to the
locked v1.0 schema, the `TIME_STATUS.state` enum, two policy files, and 148
normative lines to the compact mapping; v1.1.18 added
`policy/command-evidence.yaml`.

Each tagged tree's own `release/RELEASE_NOTES_v<version>.md` is accurate, so
the tagged v1.1.18 tree contradicts itself. **The release notes, not the
README, are the authoritative record of what a cut changed.**

Published assets and their checksums are immutable and were not rewritten.
The correction rolls forward from `main`. Full errata in `CHANGELOG.md`.

## Current-facing claims are now machine-checked

The release-currency guard pinned version *literals*; the prose beside them
was invisible to it, which is how a focus bullet survived two cuts. It now
also pins content:

- the release-focus bullet must name at least one artifact this release
  introduced and no earlier release mentioned;
- any negative governance claim it makes must appear in this release's own
  notes.

Four unpinned current-release literals found by the pre-cut review are now
covered — the README title line, the CI workflow's compatibility target, the
Tools block, and the `release/README.md` worked example. One was already
wrong: `adapters/README.md` had been pointing at `--target v1.1.16` for two
releases. A stale CI target is the one that matters most: it leaves the
workflow checking migration compatibility against the previous release while
still reporting green.

The release manifest and the bundle builders are also bound together now — a
manifest that hashes a path no bundle carries is a claim the release cannot
back. That check found the new export directory missing from both builders
before this cut shipped.

## Verification integrity

`gateway/tests/vacuity.py` closes a narrow hole with a wide history: a
doctoring step whose substitution silently changes nothing, so the guard it
was meant to prove is asked about unmodified content and passes for the most
boring possible reason. Seven instances of that broader class — a check that
passes for a reason other than the one claimed — are recorded in
`docs/zmeta_doctrine_review_log.md` under P2-D1, spanning test pins, shipped
tooling, and audit evidence.

The audit playbook's discipline on this changed as a result: a guard's
demonstration must now be an artifact in the repository, re-running in CI,
rather than an act performed once in a session and attested to in a commit
message.
