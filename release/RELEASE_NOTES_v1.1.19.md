# ZMeta v1.1.19 Release Notes

Release date: 2026-07-28
Release type: consumer-access and verification-integrity cut — the governed
policy as JSON, bundles that carry what the manifest claims, and a content
guard rebuilt after the first one was defeated

## Summary

v1.1.19 is a small release that took two rounds to get right, and the second
round is the more useful story.

One new artifact: `export/policy/*.json`, the governed policy verbatim, in a
format a consumer outside the Python stack can read. It exists because a
fielded deployment had been hand-copying governed data — not from
carelessness, but because copying was the only path this repository offered.

Everything else came from review. A downstream consumer reported a defect in
our published records; an independent panel then found that the guard written
to prevent that defect did not work, that the release bundles omitted files
the manifest declared shipped, and that a policy file containing a YAML `.inf`
would have shipped unparseable JSON with every gate green.

No governed artifact changed in this release: schema, policy data, the
semantic contract and the extension registry are byte-identical to
zmeta-v1.1.18. The locked v1.0 kernel is unchanged.

## The governed policy, readable without a YAML parser

`export/policy/*.json` is a generated, verbatim JSON projection of
`policy/*.yaml` — one file per source file, same name, same data, nothing
renamed, filtered, flattened, or interpreted. `yaml.safe_load` of a source and
`json.load` of its export compare equal, and a test pins that per file.

- Generated by `tools/export_policy_json.py`; verify with `--check`.
- Hash-pinned in the release manifest under the `policy_json_export` group.
- Provenance in `export/policy/index.json`.
- **Authority is one-directional.** `policy/*.yaml` is the source of truth.
  Editing a JSON file here does not change policy; it produces a stale file
  that `--check` fails on.

**If you maintain a hand-copy of the governed vocabularies, consume this
instead** and regenerate on each version advance rather than re-verifying an
alignment by hand.

A non-finite float in a policy file — YAML `.inf` or `.nan` — now fails
generation loudly. Python's JSON encoder would otherwise emit bare `Infinity`,
which is not JSON: `JSON.parse` throws on the whole file, and every gate stays
green because Python reads it back as `float('inf')`. That is precisely the
consumer this artifact serves, so the silent path is closed.

## The bundles now carry what the manifest declares

The release manifest hashes a set of artifacts. Nothing checked that the
downloadable bundles actually contained them, and they did not. Every bundle
now carries, and a test binds the manifest to the builders with no exception
list:

- `export/policy/` and its generator.
- **The governance documents** — `AGENTS.md`, `CONFORMANCE.md`,
  `CONTRIBUTING.md`, `IP_POLICY.md`, `TRADEMARK.md`,
  `docs/zmeta_change_governance.md`, `docs/zmeta_defensive_publication.md`.
  These are the documents that keep a downstream implementation from becoming
  a private dialect by accident. `README.md` tells clone users to read
  `AGENTS.md` before altering schema or policy, and no bundle contained it.
- **The conformance corpus** in the dist bundle — the artifact an implementer
  checks themselves against.
- The release templates the shipped release tooling consumes.
- `release/governed-baseline.yaml`, so a consumer can verify the governance
  claim below rather than trust it.

The dist bundle also shipped `validate_conformance.py` without the ten
sub-validators its own flags invoke. Those now ship. **Known limitation,
pre-existing and not closed in this release:** those validators import the
reference gateway at module load, and the dist bundle still does not carry
`gateway/`, so running them from the dist zip fails on import. The edge and
gateway bundles are unaffected. Tracked for the next cut.

## Current-facing claims are machine-checked

The release-currency guard pinned version *literals*; the prose beside them
was invisible, which is how a "Release focus" bullet describing v1.1.16
survived two cuts asserting a governance claim that was false for both. The
errata for that is below.

**The first content guard shipped in this cycle did not work, and was
replaced before release.** It tried to infer truth from prose: "names
something this release introduced" was satisfied by backticking the version
number, and the governance-claim check knew exactly one phrasing, so
"Schema, policy, and event vocabulary are unchanged" evaded it. Two one-word
edits passed a bullet carried forward wholesale.

The replacement follows the contract's own rule that structure is
authoritative and free text is a projection:

- the governance sentence is **computed** from the release manifest against
  `release/governed-baseline.yaml` and must appear **verbatim**. It cannot be
  paraphrased, because an allowlist does not care how many phrasings exist.
- the "introduced" rule reads **real artifact paths** added or changed since
  the baseline release, so a version literal cannot satisfy it.

Both are red-demonstrated against the exact inputs that defeated the first
design. Four previously unpinned current-release literals are now covered —
the README title line, the CI workflow's compatibility target, the Tools
block, and `release/README.md`'s worked example — plus `tools/README.md`'s
worked commands. One was already wrong: `adapters/README.md` had been
pointing at `--target v1.1.16` for two releases.

## Record correction: the published v1.1.17 and v1.1.18 READMEs

Both published trees carry a stale README "Release focus" bullet describing
v1.1.16's external capture corpus and asserting that no schema, policy or
event vocabulary changed. That was true of v1.1.16 and **false of both
releases that inherited it**: v1.1.17 added three `reason_code` values to the
locked v1.0 schema and the `TIME_STATUS.state` enum, amended
`policy/semantics.yaml` and `policy/violation-codes.yaml`, and added a
normative clause to the compact mapping; v1.1.18 added
`policy/command-evidence.yaml`.

Each tagged tree's own `release/RELEASE_NOTES_v<version>.md` is accurate, so
the tagged v1.1.18 tree contradicts itself. **The release notes, not the
README, are the authoritative record of what a cut changed.**

Published assets and their checksums are immutable and were not rewritten.
The correction rolls forward from `main`. Full errata in `CHANGELOG.md`.

## Also in this release

- `policy/README.md` now names `command-evidence.yaml` and
  `profile-precision.yaml` — two governed files the pack's own index had never
  listed — and a test pins that list against the directory.
- `gateway/tests/vacuity.py` refuses a doctoring substitution that changes
  nothing, closing the way a hand-run verification can report success having
  proven nothing.
- The audit playbook's discipline on guards changed: a guard's red
  demonstration must now be an artifact in the repository, re-running in CI,
  rather than an act performed once and attested to in a commit message.
  Rationale and the seven instances behind it are in
  `docs/zmeta_doctrine_review_log.md` under P2-D1.

## Compatibility

- `tools/check_compat.py` gains the `v1.1.19` target.
- Current-facing documents re-baseline to the v1.1.19 release manifest.
- Nothing previously valid becomes invalid.
