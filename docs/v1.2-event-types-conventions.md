# v1.2 event-type conventions

**Status:** Proposed for v1.2.0. **Conventions, not vocabulary changes.**

ZMeta v1.2 introduces **no new `event_type` values.** The six v1.1 types
remain authoritative:

| `event_type` | Use for |
|---|---|
| `OBSERVATION_EVENT` | A sensor's direct measurement of something in the world. |
| `INFERENCE_EVENT` | A processed conclusion drawn from one or more observations (classification, correlation, identification). |
| `FUSION_EVENT` | A multi-source synthesized estimate (e.g., a fused track whose position is computed from contributing sensors). |
| `STATE_EVENT` | The current state of an entity (asset position, comms node mode, task definition). Typically retained on MQTT. |
| `COMMAND_EVENT` | An imperative directed at an entity or service (task assignment, transport control, send-text). |
| `SYSTEM_EVENT` | Operational events about the system itself (heartbeats, metrics, node health, broker election). |

What v1.2 adds is two `event_subtype` **conventions** under
`INFERENCE_EVENT` that define how fusion engines propagate correlation
assignments to contributing sensors. Both work with `event.correlation`
from the envelope (see `spec/correlation-semantics.md`).

These are **conventions, not new event_types.** Any v1.2-aware consumer
recognizes them by `event_subtype`. v1.1 consumers would see them as
unknown subtypes and (depending on their handling) either drop or log
them.

## `bond_assigned`

**Purpose:** Tell a sensor that one or more of its local tracks has
been correlated to a stable `correlation_id`. The sensor updates its
internal `local_track_id → correlation_id` map and includes
`event.correlation.correlation_id` on subsequent observations for that
local_track_id.

**Topic convention (MQTT):** `inference/bond_assigned/<sensor_id>`,
retained, QoS 1.

**Payload shape:**

```json
{
  "sensor_id": "<sensor_id>",
  "bonds": [
    {
      "local_track_id": "<sensor's internal id>",
      "correlation_id": "<stable fused id>",
      "primary_alias": { "scheme": "MMSI", "value": "..." },
      "aliases": [ { "scheme": "ICAO24", "value": "..." } ],
      "fusion_revision": 2
    }
  ]
}
```

## `bond_dissolved`

**Purpose:** Tell a sensor that a previously-bonded correlation has
been split or otherwise dissolved.

**Atomic-split semantics:** A single `bond_dissolved` event carries
both the dissolved bonds AND any replacement bonds the same
dissolution produced. Consumers MUST NEVER see a split as a two-message
sequence. This is the core invariant: the event represents a
state-transition, not a partial change.

**Topic convention (MQTT):** `inference/bond_dissolved/<sensor_id>`,
not retained.

**Payload shape:**

```json
{
  "sensor_id": "<sensor_id>",
  "dissolved": [
    {
      "local_track_id": "<sensor's internal id>",
      "former_correlation_id": "<previous fused id>"
    }
  ],
  "new_bonds": [
    {
      "local_track_id": "<sensor's internal id>",
      "correlation_id": "<new fused id>",
      "primary_alias": { "scheme": "internal", "value": "..." },
      "aliases": [ { "scheme": "internal", "value": "..." } ]
    }
  ]
}
```

`new_bonds` MAY be empty if the dissolution leaves the local track
unbonded. The next observation for that local_track_id will get
re-bonded (or not) as if cold-started.

## Compatibility

A v1.1 consumer encountering these subtypes sees a known
`INFERENCE_EVENT` with an unfamiliar `event_subtype`. Most v1.1
consumers either (a) ignore unknown subtypes, or (b) route them to a
generic INFERENCE handler. Either way, no validation failure occurs.

A v1.2 fusion engine producing these events on v1.1-only deployments
provides no benefit (sensors won't act on them) but causes no harm.
